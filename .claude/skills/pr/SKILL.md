# Задача → ветка → PR

**В `main` напрямую не коммитим.** Каждая задача — своя ветка и Pull Request:
второй участник смотрит diff и мёржит. Это защищает чужую работу.

## 1. Начать от свежего main
```bash
cd /home/alex/projects/DPmodule
git checkout main && git pull --ff-only
git checkout -b <тип>/<задача>      # feat/… fix/… chore/… docs/…
```
Проверить, что реально на ветке: `git branch --show-current`.

⚠️ **Ветки не штабелировать.** Не делать ветку от другой неслитой ветки: PR
вольётся в свою базу, а не в `main`, и работа зависнет (так уже случалось). Каждая
задача — от `main`. Если ветки всё же связаны, сливать строго по порядку и удалять
базовую ветку на GitHub после мержа.

## 2. Сделать правку
- Одна ветка — одна логическая задача (подсистема / 1–2 связанных файла).
- Работать **только в своей папке-клоне**; в чужой не редактировать и git-команды
  не запускать.
- Правила проекта (`CLAUDE.md`, `PROJECT_INSTRUCTIONS.md`, `TARGET.md`) главнее
  привычных умолчаний: никакого нового хардкода портов, время — МСК naive,
  GORM-гибрид, минимальное изменение вместо переписывания модуля.

## 3. Проверки (до коммита)
```bash
go build ./...
go test ./...
go vet ./internal/...
```
Если трогали фронт — из `frontend/`:
```bash
npx ng build --configuration development
```
Красное не коммитим. Если тест падал до правки — сказать об этом явно, не выдавать
за успех.

## 4. Обновить STRUCTURE.md
**В той же ветке.** Добавили/удалили/переименовали файл или сменили его назначение
— обновить `STRUCTURE.md`. Это справочник владельца, устаревать ему нельзя.

## 5. Показать diff и спросить подтверждение
Перед коммитом показать, что меняется, и получить «да». Отдельно проверить, что не
уезжают секреты:
```bash
git status --short
git check-ignore .env && echo ".env игнорится ✓"
```
`.env`, `_reference/seed/*.csv`, реальные креды и chat_id в git не попадают.

## 6. Коммит и пуш
Сообщение — по-русски, по существу: что изменилось и **почему**, отход от gtport
или от плана отмечать явно. Заканчивать строкой:
```
Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
```
```bash
git commit -F - <<'EOF'
<тип>(<область>): <суть>

<детали: что и почему; решения владельца; что осознанно НЕ сделано>

Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
EOF
git push -u origin <ветка>
```

## 7. Создать PR
Сразу после пуша, без отдельного вопроса — это часть штатного потока:
```bash
gh pr create --base main --head <ветка> --title "<заголовок>" --body "$(cat <<'EOF'
<что и зачем; как проверено; что осознанно не вошло>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```
Отдать владельцу ссылку на PR.

## 8. После мержа
```bash
git checkout main && git pull --ff-only
git branch -d <ветка>
```

## Если случайно закоммитил в main
Проверить, ушло ли в удалённый (`git rev-list --count origin/main..HEAD`). Пока не
запушено — чинится без потерь:
```bash
git branch <ветка>            # сохранить коммит на ветке
git reset --hard origin/main  # откатить локальный main
git checkout <ветка>
```
Сказать владельцу прямо, что произошло и что исправлено.
