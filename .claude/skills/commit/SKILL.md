# Задача → проверки → коммит

Проект ведёт один человек, поэтому **коммитим прямо в `main`**. Ветка и Pull Request
— не обязательный ритуал, а инструмент на случай, когда `main` нужно сохранить
пригодным к раскатке (см. §7).

⚠️ **Гейт — не коммит, а `git push`.** `origin/main` — источник деплоя: скил
`/deploy` на VPS делает `git pull`, а там с базой прямо сейчас работает диспетчер.
Инвариант: **всё, что ушло в `origin/main`, пригодно к раскатке.** Локальные коммиты
— свободно, пуш — только на зелёных проверках.

## 1. Синхронизироваться
```bash
cd ~/projects/DP/DPmodule
git checkout main && git pull --ff-only
```
Проверить, где реально находимся: `git branch --show-current`.

## 2. Сделать правку
- Один коммит — одна логическая задача (подсистема / 1–2 связанных файла).
- Работаем **на одной машине за раз**; уходя с неё, ничего незапушенного не
  оставляем. Писать код лучше в WSL (копия базы, `go test`, выключенные интеграции).
  Правили на VPS — коммит и `push` сразу: незакоммиченная правка там либо заблокирует
  следующий `pull`, либо молча разойдётся с git, потому что `go build` собирает
  из рабочего дерева и правка уедет в боевой бинарь.
- Правила проекта (`CLAUDE.md`, `PROJECT_INSTRUCTIONS.md`, `TARGET.md`) главнее
  привычных умолчаний: никакого нового хардкода портов, время — МСК naive,
  GORM-гибрид, минимальное изменение вместо переписывания модуля.

## 3. Проверки (до пуша)
```bash
go build ./...
go test ./...
go vet ./internal/...
```
Если трогали фронт — из `frontend/`:
```bash
npx ng build --configuration development
```
Красное не пушим. Если тест падал до правки — сказать об этом явно, не выдавать
за успех.

## 4. Обновить STRUCTURE.md
**В том же коммите.** Добавили/удалили/переименовали файл или сменили его назначение
— обновить `STRUCTURE.md`. Это справочник владельца, устаревать ему нельзя.

## 5. Показать diff и спросить подтверждение
Перед коммитом показать, что меняется, и получить «да». Отдельно проверить, что не
уезжают секреты:
```bash
git status --short
git check-ignore .env && echo ".env игнорится ✓"
```
`.env`, `config.local.yaml`, `_reference/seed/*.csv`, реальные креды и chat_id
в git не попадают.

## 6. Коммит и пуш
Сообщение — по-русски, по существу: что изменилось и **почему**, отход от gtport
или от плана отмечать явно. Заканчивать строкой:
```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```
```bash
git commit -F - <<'EOF'
<тип>(<область>): <суть>

<детали: что и почему; решения владельца; что осознанно НЕ сделано>

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
EOF
git push
```
Если `push` отбит (`non-fast-forward`) — на GitHub есть чужие коммиты:
`git pull --rebase` и повторить.

## 7. Когда всё-таки ветка
Ветка нужна там, где `main` должен остаться раскатываемым, пока работа не готова:
- задача на несколько заходов и `main` посреди неё нерабочий;
- миграции БД, конвейер дислокации, крупный рефактор — то, откуда нужен чистый откат;
- эксперимент, который может не взлететь.

```bash
git checkout -b feat/<задача>       # feat/… fix/… chore/… docs/…
# … работа, проверки …
git checkout main && git merge --no-ff feat/<задача>
git branch -d feat/<задача>
```
`--no-ff` даёт один узел слияния — по нему потом откатывается вся задача целиком.
Ветки **не штабелировать**: каждая — от `main`.

Пушить ветку и делать PR (`gh pr create`) есть смысл только когда правку смотрит
кто-то ещё. В одиночной работе достаточно `git diff` перед коммитом (§5).

## Если запушено сломанное
`origin/main` — то, что уедет в бой, поэтому чиним сразу и в первую очередь.
Пока на VPS не сделан `pull`, дешевле всего откатить верхушку:
```bash
git revert <хэш>     # безопасно: новый коммит, история не переписывается
git push
```
Сказать владельцу прямо, что произошло и что исправлено. Если `pull` на VPS уже
прошёл — сначала `/deploy` с откаченным кодом, потом разбор.
