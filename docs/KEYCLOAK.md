# Keycloak: realm `iqport` — контекст для разработки DPPort

Документ описывает актуальное состояние Keycloak-реалма, в котором живёт DPPort.
Читай его перед любой задачей, связанной с авторизацией, ролями, токенами или защитой эндпоинтов.

> Составлено по фактическому состоянию админ-консоли. Разделы, помеченные `TODO`, содержат
> неподтверждённые данные — уточни у разработчика прежде чем полагаться на них.

> ✅ Исправлено 03.08.2026 по discovery живого сервера: issuer — ДОМЕННЫЙ
> (`KC_HOSTNAME=uport1.ru`), хотя Keycloak отвечает и по IP `85.209.9.182:8443`.
> В исходной версии документа здесь стоял issuer с IP — с ним валидация токена
> падает: `iss` в токене сравнивается дословно.

| Параметр | Значение |
|---|---|
| Base URL Keycloak | `https://uport1.ru` (тот же хост: `85.209.9.182`, admin-порт `:8443`) |
| Realm name (в URL) | `iqport` |
| Display name (только в UI) | `IQPort` |
| Issuer | `https://uport1.ru/realms/iqport` |

**Realm name в URL — `iqport` в нижнем регистре.** Не `IQPort`. Регистр критичен, ошибка даёт 404
на discovery-эндпоинте.

Эндпоинты (из discovery, проверено 03.08.2026):

```
Discovery : https://uport1.ru/realms/iqport/.well-known/openid-configuration
Authorize : https://uport1.ru/realms/iqport/protocol/openid-connect/auth
Token     : https://uport1.ru/realms/iqport/protocol/openid-connect/token
UserInfo  : https://uport1.ru/realms/iqport/protocol/openid-connect/userinfo
Logout    : https://uport1.ru/realms/iqport/protocol/openid-connect/logout
JWKS      : https://uport1.ru/realms/iqport/protocol/openid-connect/certs
```

Никогда не хардкодь эти URL по отдельности — бери `issuer` из конфига и собирай остальное через
discovery.

⚠️ С машины разработчика (WSL) `https://uport1.ru` отвечает 403 (гео-блокировка
на edge) — стендовый Keycloak локально не потестировать, dev-контур живёт на
локальном Keycloak (`docs/DEV_WSL.md`).

## 2. Клиенты, относящиеся к DPPort

В реалме три клиента с отношением к DPPort:

| Client ID | Назначение | Home URL |
|---|---|---|
| `iqport-dpport` | Основной. Фронтенд DPPort, прод | `https://dpport.iqport.ru` |
| `dpport-develop` | Дев-окружение | — |
| `iqport_dpport_service` | Service account для бэкенда | — |

Все три — OpenID Connect.

**`iqport-dpport`** — то, через что логинится пользователь в браузере. Публичный клиент
(проверь `Client authentication` на вкладке Settings: выключено = public).

**`iqport_dpport_service`** — для межсервисных вызовов без пользователя: бэкенд DPPort ходит
в другие сервисы контура от своего имени через `grant_type=client_credentials`. Секрет лежит на
вкладке Credentials. **Секрет не коммитить**, он идёт через переменные окружения.

Обрати внимание на разделитель: у сервисного клиента подчёркивания (`iqport_dpport_service`),
у остальных дефисы (`iqport-dpport`). Легко опечататься.

## 3. Ролевая модель — как она устроена на самом деле

### 3.1 Все роли — realm roles

В реалме **нет ни одной client role**. Все 17 ролей объявлены на уровне realm.

Практическое следствие для кода DPPort:

```jsonc
// Роли лежат ЗДЕСЬ:
{
  "realm_access": {
    "roles": ["operator_dpport", "view_sspr", "view_rtport", "offline_access"]
  }
}

// А ЗДЕСЬ ролей приложений НЕТ (только служебные account-роли):
{
  "resource_access": {
    "account": { "roles": ["manage-account", "view-profile"] }
  }
}
```

Читай `realm_access.roles`. Не пиши парсер `resource_access["iqport-dpport"].roles` — он всегда
вернёт пусто.

### 3.2 Роли DPPort

| Роль | Описание в Keycloak | Смысл |
|---|---|---|
| `admin_dpport` | — | Администратор DPPort |
| `operator_dpport` | — | Оператор |
| `client_dpport` | — | Клиент (внешний контрагент) |
| `client_dispatcher_dpport` | — | Клиент-диспетчер |

Описания в Keycloak пустые — семантику знает только код. Это и есть источник истины,
поэтому фиксируй её в коде явно, комментарием рядом с константой.

**DPPort использует модель «по типу пользователя», а не «по действию».** У остальных приложений
контура (`mpport`, `rtport`, `sspr`) роли устроены как `edit_*` / `view_*`. У DPPort — четыре роли
по роду занятий. Ролей `edit_dpport` и `view_dpport` не существует. Не изобретай их.

### 3.3 Чужие роли в токене — игнорировать

Так как все роли realm-уровня, в токене пользователя DPPort приедут и роли других приложений.
Реальный пример: группа `profiles/dpport-operator` выдаёт `operator_dpport`, `view_sspr` **и**
`view_rtport`.

Полный список ролей реалма, чтобы понимать, что может прилететь:

```
DPPort  : admin_dpport, operator_dpport, client_dpport, client_dispatcher_dpport
MPPort  : edit_mpport, view_mpport
RTPort  : edit_rtport, view_rtport
SSPR    : edit_sspr, view_sspr
Общие   : admin, manager, dispatcher, operator      // см. 3.4
Служебн.: offline_access, uma_authorization, default-roles-iqport
```

Бэкенд DPPort должен проверять **только** свои четыре роли и молча игнорировать остальные.
Не пиши логику вида «если нет ни одной известной роли — 403 с перечислением», это сломается
при добавлении нового приложения в контур.

### 3.4 Легаси-роли — не использовать

Роли `admin`, `manager`, `dispatcher`, `operator` — без привязки к приложению, остались от времён,
когда сервис был один. Единственные роли с человеческими описаниями (Администратор, Руководитель,
Диспетчер, Оператор), что подтверждает их возраст.

**Не завязывай на них новую логику DPPort.** Если в существующем коде найдётся проверка на `operator`
вместо `operator_dpport` — это баг: роль `operator` может быть выдана пользователю совсем другого
приложения, и он получит доступ к DPPort. Помечай такие места и выноси в отдельный список на ревью,
но не переписывай молча — возможно, на них завязан FPPort (см. раздел 6).

Обрати внимание на ловушку именования: `operator` и `operator_dpport` — разные роли. Одна проверка
на `startsWith("operator")` пропустит чужого.

### 3.5 Роли по умолчанию

Composite-роль `default-roles-iqport` выдаётся всем пользователям реалма автоматически и содержит:

```
account:manage-account
account:view-profile
uma_authorization
```

Ничего прикладного там нет. `offline_access` в неё **не входит** — offline-токены выдаются только
явно. Не полагайся на наличие `offline_access` у произвольного пользователя.

## 4. Группы: откуда пользователь берёт роли

Роли пользователям почти не назначают напрямую. Используется модель «группа = профиль доступа»:
пользователя кладут в группу, роли приходят по членству. Composite-роли при этом не применяются
(все роли `Composite = False`).

Дерево групп смешивает две оси:

```
attis            ← организация / тенант
gut-2            ← организация / тенант
ut-1             ← организация / тенант
mpport-managers  ← профиль (лежит не на своём месте, см. ниже)
mpport-operators ← профиль (лежит не на своём месте, см. ниже)
profiles/
  client
  client-dispatcher
  dpport-admin
  dpport-operator
  observers
  rtport-dispatcher
  sspr-dispatcher
```

Профили, относящиеся к DPPort: `profiles/dpport-admin`, `profiles/dpport-operator`,
`profiles/client`, `profiles/client-dispatcher`.

Подтверждённый состав одного из них:

```
profiles/dpport-operator → operator_dpport, view_sspr, view_rtport
```

`mpport-managers` и `mpport-operators` логически тоже профили, но лежат в корне, а не внутри
`profiles/`. Это известная неаккуратность, к DPPort прямого отношения не имеет.

Группа `attis` / `gut-2` / `ut-1` отвечает на вопрос «чьи данные видит пользователь»,
профиль — «что он может делать». Если DPPort должен разграничивать данные по организациям,
членство в группе надо прокидывать в токен отдельным маппером — **сейчас такого маппера нет**,
в токене группы не окажется. См. раздел 7.

## 5. Работа с токеном

### Фронтенд

Роль не является источником истины для безопасности — она только для UI (спрятать кнопку,
скрыть раздел меню). Любая проверка на фронте дублируется на бэке.

Не декодируй `access_token` руками для бизнес-логики. Если нужны данные профиля — бери из
`id_token` или `userinfo`.

### Бэкенд

Валидация обязательна на каждом запросе:

1. Подпись — по ключам из JWKS-эндпоинта, с кэшированием и ротацией по `kid`.
2. `iss` — точное совпадение с `https://uport1.ru/realms/iqport`.
3. `exp` / `nbf`.
4. `aud` или `azp` — ✅ подтверждено живым токеном (03.08.2026): `aud` =
   `["iqport-dpport", "account"]`, в конфиге DPPort проверка `audience` включена.

Никогда не доверяй `realm_access.roles` из токена, подпись которого не проверена.

### Практический приём для отладки

Самый быстрый способ увидеть, что реально окажется в токене у конкретного пользователя, —
админ-консоль: **Clients → iqport-dpport → Client scopes → Evaluate**. Выбираешь пользователя,
получаешь готовый JSON. Это снимает большинство вопросов «почему роль назначена, а не работает».

Если роль назначена, но в токене её нет — причина почти всегда в `Full scope allowed`
(Clients → iqport-dpport → Client scopes → Scope). При выключенном флаге в токен попадают только
явно добавленные в scope роли.

## 6. Известные проблемы контура

Это не задачи DPPort, но знать о них полезно — они объясняют странности.

**У FPPort нет ролей вообще.** Клиент `iqport-fpport` существует, а ни одной роли под него в реалме
не заведено. Либо сервис пускает любого аутентифицированного, либо завязан на легаси-роли из 3.4.
Это причина, по которой легаси-роли нельзя просто удалить.

**DPPort выбивается из общей модели.** Остальные приложения используют `edit_*` / `view_*`.
Обсуждается приведение DPPort к той же схеме. Миграция потребует правки кода, поэтому:

> **Держи имена ролей в одном месте.** Один модуль констант на фронте, один на бэке.
> Строковые литералы `"operator_dpport"` не должны быть разбросаны по контроллерам и компонентам.
> Когда дойдёт до переименования, цена вопроса — правка двух файлов, а не аудит всего репозитория.

## 8. Правила для генерации кода

1. Роли читать из `realm_access.roles`, не из `resource_access`.
2. Использовать только четыре роли DPPort. Чужие роли в токене — норма, игнорировать без ошибок.
3. Имена ролей — только через модуль констант, никаких строковых литералов по коду.
4. Не изобретать роли `edit_dpport` / `view_dpport` — их не существует.
5. Не завязываться на легаси-роли `admin`, `manager`, `dispatcher`, `operator`.
6. Проверка прав на фронте — только для UI. Каждый защищённый эндпоинт проверяется на бэке.
7. URL Keycloak — из конфигурации через discovery, не хардкодить IP.
8. Секрет `iqport_dpport_service` — только из переменных окружения.
