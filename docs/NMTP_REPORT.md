# Отчёт «Подход вагонов» по форме порта (НМТП)

Перенос gtport PortReportNmtp с унификацией. Эталон формы — файлы порта
«ПОДХОД ВАГОНОВ ГУТ-2 (1).xlsx» и «ПОДХОД ВАГОНОВ УТ-1.xlsx» (лист = сутки;
подтверждены владельцем как актуальные 29.07.2026). Для АЭ файла порта нет —
раскладка по gtport (6 колонок СУЭК + ЭЛЬГА).

## Как устроено

- **Строки** — поезда в подходе с отбором «Подхода»: получатель ИЛИ назначение
  = терминал, есть прогноз, не прибывшие (статусы 10/12 исключены). Так устроен
  сам файл порта: поезда «НА АТТИС» стоят в листе ГУТ-2 с пометкой (в gtport
  НМТП фильтровал строго по назначению — осознанный отход). Пометка перестановки
  выводится в колонке «ПРИМЕЧАНИЕ» (в файле порта эта колонка называлась
  «СУДНО», но жили в ней именно пометки «НА АТТИС»/«С АТТИСА»). Там же —
  смена индекса «был NNN» (середина `index_main`, когда текущий индекс не
  равен ему — перенос gtport `buildPrimFields`); вместе — через запятую:
  «был 170, С ГУТ-2».
- **Секции** — станции терминалов из реестра `ports` (Мыс Астафьева, Находка),
  затем дороги дислокации с востока на запад (ДВС → ЗАБ → ВСБ → КРС → ЗСБ →
  ЮУР → СВР; неизвестная дорога — в конец, поезд не теряется). Внутри секции —
  по прогнозу по возрастанию. Ниже — та же структура для брошенных (признак —
  вагон статуса 5 в составе; дата бросания из `bros`, в колонке прибытия —
  как в файле порта).
- **Колонки** — справочник `nmtp_column` (миграция 000053, правится в Админе):
  три подписи шапки (клиент / станции / марка — как в файле) + правила
  матчинга по натуральным полям вагона: `client`, `station_nach`, марка.
  Вагон идёт в самую СПЕЦИФИЧНУЮ совпавшую колонку (больше заданных правил —
  раньше проверка; «СЛЯБЫ» побеждает «ПРОКАТ» без марки), не сматчившиеся
  падают в автоколонку «ПРОЧЕЕ» с подсветкой — громко, а не молча.
  gtport-механика (`marka.sprav_1` + хардкод-маппинг) не переносилась:
  sprav_1 в DPmodule пуст (осознанно, миграция 000032).
- **Марка груза** — код ЕТСНГ её не различает (весь угольный концентрат —
  161043), марка живёт только в свободном тексте `freight_exact_name`
  («КОНЦЕНТРАТ УГОЛЬНЫЙ Ж», «...МАРКА ГЖ+Ж.», написания пляшут). Нормализатор
  (`service.MarkNormalizer`) ищет известные марки (словарь `nmtp_mark`,
  правится в Админе) по границам слова, длинные первыми; фолбэк — `cargo_sms`
  словаря cargo (сортовые угли Д/Г/Т и металл ЗАГ/СЛЯБЫ/ЧУГУН/РЕЛ — там метка
  словаря и есть продукция). Новое написание марки = строка в `nmtp_mark`.
- **Подвал** — вагоны и тоннаж по колонкам (тоннаж ФАКТИЧЕСКИЙ по `ves`, а не
  gtport-овские 0.07×вагоны), счётчики поездов, «Прогноз выгрузки по подходу»
  (формула из файла: вагоны терминальных станций + ДВС + ЗАБ + ВСБ, делённые
  на 7), «Нагрузка на ж/д сеть» (норма — `ports.nmtp_norm`: ГУТ-2 2600,
  УТ-1 3500; 0 — блок не печатается), свод тоннажа по клиентам.
- **Время** — «ожид. дата/время приб.» в книге ВЛАДИВОСТОКСКОЕ (решение
  владельца 29.07.2026: порт живёт в местном времени). Единственное место
  сдвига во всём проекте — `report.vladTime` (+7 при рендере); данные и все
  остальные экраны — Московские naive (TARGET §3.11).

Ручка: `GET /reports/nmtp/excel?terminal=` (книгу собирает сервер),
`GET /reports/nmtp/terminals` — терминалы с настроенной раскладкой (кнопки
карточки «Отчёты НМТП» на «Справках и отчётах»).

## Проверено (30.07.2026, копия боевой базы + листы порта 29.07)

- Общие поезда листа порта и нашей книги легли в одинаковые колонки
  (ОС+К Междуреченска, Петровский, Чегдомын, металл-заготовка).
- Формула прогноза сходится (наша: 756/7 = 108 при 898 вагонах ГУТ-2).
- «ЛЕН-КУЗН 1/2» у порта — колонки ПО МАРКЕ (Г / Д,ДОМСШ), а не по номеру
  станции: сверка листа показала поезда со ст. Ленинск-Кузнецкий 1 маркой Д
  в колонке «ЛЕН-КУЗН 2» — правила seed так и заведены.
- На текущем снимке обе формы раскладываются без «ПРОЧЕЕ» (все вагоны
  сматчились правилами).

## Правила владельца 30.07.2026 (после сверки с выгрузкой gtport по АЭ)

- **Состав короче 20 вагонов — не поезд**: в счётчиках «кол-во поездов в
  движении / брошенных» не участвует (константа `nmtpMinTrainVagons`); строку
  формы, вагоны и тоннаж получает полностью. В gtport та же идея жила порогом
  «>25» в формуле листа.
- **«Ожид. дата/время приб.» — только плановым поездам** (в поезде есть вагон
  с `plan_jd`); печатается прогноз (`prog_jd`), бесплановым — пусто.
- **Режим «скрыть перестановки»** (`mode=naznach`, gtport UseNaznachOnly):
  отбор строго по назначению — без поездов, переставляемых на соседний
  терминал. Актуален для терминалов одной станции (АЭ/ГУТ-2). По умолчанию —
  получатель ИЛИ назначение, с пометками «С/НА {терминал}».
- **Ключ строки — индекс + станция + прогноз** (как L1-ключ «Подхода»):
  безиндексные «Б/И» поезда на разных станциях — отдельные строки (баг
  слипания найден сверкой 30.07: 5 поездов Б/И печатались одной строкой).

## Редактор (решение владельца 30.07.2026)

- **Правки отчёта нигде не хранятся** — живут только на экране модалки:
  ПКМ по строке (изменить поля/счётчики, убрать строку), «+» в полосе секции
  (своя строка). Итоги пересчитываются локально; тоннаж остаётся серверным
  (весов у ручных цифр нет). Excel с правками — `POST /reports/nmtp/excel`
  правленым отчётом, книга собирается тем же рендером; «Обновить» и смена
  режима правки сбрасывают.
- **Единственное, что хранится, — привязка «вагон → колонка»**
  (`nmtp_vagon_column`, миграция 000055): указание грузовладельца «считать
  этот поезд другой категорией» — факт про вагоны. ПКМ → «Переместить в
  колонку…» пишет привязку поимённо по номерам состава; при раскладке она
  сильнее правил `nmtp_column`, поэтому переживает переформирование поезда.
  Хранится: номер вагона, колонка, когда и кто назначил. Объём — десятки
  строк (вагоны с действующим указанием), не история.
- **Жизненный цикл привязки** (вопрос владельца 30.07.2026) — три механизма
  гашения при построении отчёта, все best-effort (сбой не роняет отчёт):
  1. **новый рейс**: дата приёма вагона к перевозке позже привязки — привязка
     старого рейса протухла, вагон ложится по правилам, запись удаляется
     (в любом режиме — распознание положительное);
  2. **выпал из подхода** (прибыл/выбыл): удаляется в режиме по умолчанию;
     в naznachOnly выключено — скрытые отбором перестановки «НА {сосед}» живы;
  3. **страховка по возрасту**: всё старше 60 суток (`nmtpBindingMaxAge`) —
     ловит сирот, если отчёт долго не строили.
  Плюс ручное «вернуть по правилам» в модалке.
