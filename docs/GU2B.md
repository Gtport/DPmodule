# ГУ-2б — источник факта выгрузки

_Решение владельца 17.08.2026: учёт выгрузки переходит с косвенных признаков
(порожний / выбытие из снимка) на уведомления ГУ-2б о завершении грузовой
операции. Обоснование — анализ корпуса провайдера: покрытие ~97% (с дозабором
≈99.7%), терминал выгрузки совпал с ручным учётом gtport на 100% из 4337
рейсов, включая все перестановки АЭ↔ГУТ-2 (11–15% рейсов). Здесь — контракт
отдачи, устройство приёма и порядок включения._

## Контракт отдачи (опубликован владельцем 17.08.2026)

```
GET <base_url>/{client}/gu2b/update?since=<t>&limit=<n>
```

- `client` — код клиента провайдера (`attis`/`nmtp`), как у памяток.
- `since` — курсор: дословный `LAST_UPDATE` прошлого непустого ответа
  (`YYYY-MM-DD HH:MM:SS.sss`). **`since=0` — полная перезаливка** с начала
  накопления.
- `limit` — не больше стольких уведомлений в ответе; полную страницу dpport
  дочитывает в том же тике.
- Инкремент — по `max(created_at, updated_at)` уведомления; отдаются **все
  состояния** документов (фильтрует принимающая сторона).
- Авторизация — как у остальных ручек провайдера (Keycloak Bearer / X-API-Key).

Ответ (стиль `reference/update` самого провайдера — UPPER_SNAKE, имена полей —
как в его нормализованных таблицах; времена МСК naive `YYYY-MM-DD HH:MM:SS[.sss]`):

```json

      "NOTIFICATION_ID": 60383536,

      "STATE_ID": 2, "STATE": "Подписан",
      "DATE_CREATE": "2026-08-24 09:15:00",
      "STATION_CODE": "98560", "STATION_NAME": "МЫС АСТАФЬЕВА",

      "GATEWAY_SOURCE": "asu",
      "UPDATED_AT": "2026-08-24 09:21:00.123",
      "CARS": [
        { "CAR_ORDER": 1, "CAR_NUMBER": "52962537",
          "OPERATION_ID": 1, "OPERATION_NAME": "Выгрузка", "OPERATION_SHORT": "ВЫГР",
```

Разбор — `internal/parser/gu2b.go` (изолирован: живой формат разойдётся —

курсор нельзя двигать по частично разобранному ответу.

## Приём на нашей стороне

Крон `gu2b-update` (`pull_interval`, дефолт 1h, тик и при старте) — по образцу
памяток: курсор в БД (`dpport.gu2b_cursor`), сдвиг только вперёд и только на
непустой `LAST_UPDATE`, нахлёст `cursor_overlap` (30m), порог тишины
`stale_after` (12h — уведомлений ~30/сутки на клиента) в `event_journal`
(`gu2b_pull`). Ручной триггер: `POST /api/v1/gu2b/update/pull`.

Отличия от памяток:
- **Уведомления храним**: `dpport.gu2b_notification` + `gu2b_car` (миграция
  000063). Нужны для дедупа повторов против прошлых тиков, контроля полноты и
  как материал для включения перезаписи.
- **Первый заход — `since=0`** (полная перезаливка), а не окно-lookback:
  контроль нумерации требует всей ленты. Повторить перезаливку = удалить строку
  клиента из `gu2b_cursor` (данные лягут поверх идемпотентно).
- **Контроль полноты**: `NOTIFICATION_NUM` — сквозная нумерация клиента, дыры
  ловятся SQL'ем и пишутся Warn'ом в лог и в журнал. Дыры сами не закрываются —
  просить провайдера дозапросить документы из ЭТРАН (прецедент: №1293–1316
  attis, потерянные его собственным сбором).

## Движок перезаписи вех (`gu2b.apply`, по умолчанию ВЫКЛ)

`domain.ApplyGU2B` (чистая функция, тесты в `gu2b_apply_test.go`). Уточняет
`date_vigr` / `date_vigr_d` / `place_vigr` в `vagon_history`; **снимковый путь
(10→12, applyUnloadOnLeave) остаётся резервом** — он пишет веху первым,
уведомление уточняет. Правила:

| Правило | Значение |
|---|---|
| Фильтр документа | только `STATE = Подписан` |
| Фильтр строки | только операция выгрузки (`ВЫГР`/«Выгрузка»); БОП и прочее — мимо |
| Момент выгрузки t | `DATE_CREATE` (фолбэк `DOC_LAST_OPER`) |
| Замок | последний рейс вагона с прибытием-**МСК-фактом** ≤ t (`arrivalFactFromJd` — то же правило, что у памяток; без него терялось 24% уведомлений) |
| Перезапись | веха пуста → пишем; веха стоит и t ≤ веха+2мин → уточняем; позже → скип (как у АСУ) |
| Дедуп | события одного вагона ближе 72 ч = один факт, побеждает ПЕРВОЕ (эталон АСУ); повтор того же `NOTIFICATION_ID` — идемпотентная перезапись |
| `date_vigr_d` | ЖД-сутки от t: «час ≥ 18 → дата +1» |
| `place_vigr` | терминал по «ОКПО + станция ПО ИМЕНИ» (`ports.okpo` + `ports.location`; коды станций документа 5-значные и с настроечными не совпадают). Не определился — место не трогаем |
| «Недоехавшие» | рейсы с `not_arrived` пропускаются |

Причины пропусков считаются в журнале (`reasons`): `not_signed`, `not_unload`,
`no_time`, `no_trip`, `duplicate_72h`, `later`.

## Порядок включения

1. Провайдер выкатывает ручку (готовый код — в патче у владельца).
2. `gu2b.enabled: true` на бою → первый тик делает полную перезаливку;
   смотреть лог `component=gu2b` и `gu2b_pull` в журнале, проверить дыры
   нумерации.
3. Сверка накопленного с нашими вехами (расхождения = перестановки + уточнения
   времени) — по её итогам владелец решает включить `gu2b.apply: true`.
4. До включения apply вехи продолжает писать снимковый путь — ничего не
   ломается, данные просто копятся.

⚠️ Словарь операций провайдера подтверждён на одном значении («Выгрузка» →
«ВЫГР») — при сверке шага 3 посмотреть на строки с другими операциями.
