# Справка по логированию

Как в модуле устроены логи: куда пишутся, что на каком уровне и где смотреть,
когда «не работает». Соглашение принято 12.08.2026 (ветка
`fix/implementation-of-logging`), до него лог покрывал только старт приложения,
кроны и внешние интеграции.

- **Движок:** `zap`, сборка — `pkg/logger/logger.go`, свой колоночный энкодер —
  `pkg/logger/encoder.go`.
- **Настройка:** блок `log:` в конфиге стенда.
- **Куда:** stdout (journald) + файл с ротацией. Цвет — только в stdout: в файле
  «\x1b[34mINFO\x1b[0m» ломает `grep` и сборщики логов.
- **Формат:** `log.format` — `text` (по умолчанию, колонки для человека) или
  `json` (для сборщика). Формат задан ПОЛЕМ, а не выведен из `app.env`: логи
  читают одни и те же люди на всех стендах, и смена окружения не должна
  незаметно менять их вид. Наборы полей у форматов одинаковые.

## Как выглядит строка

```
<время> · <уровень> · <component> · <направление+цель> · <сообщение> · <поля>
```

```
17.08 04:58:49.129  INFO   startup                                    готов: слушаю                 addr=127.0.0.1:8080
17.08 05:05:00.340  INFO   dislocation  → АСУ 10.0.0.5:8443           дислокация получена           client=attis bytes=1.2МБ took=340мс
17.08 05:05:01.572  WARN   http         ← dispatcher1 10.0.0.14       запрос отклонён               req=36f1551e method=PUT path=/api/v1/… status=403 took=12мс
```

Колонки фиксированной ширины — чтобы глаз шёл по вертикали и одно и то же
значение всегда оказывалось на одном месте. Длительности округлены (`340мс`,
`13ч 20м`), объёмы человекочитаемы (`1.2МБ`), `request_id` в строке укорочен до
8 знаков — полное значение уходит в заголовок ответа `X-Request-Id` и в json.

## Словарь `component`

Закрытый список предметных областей (`pkg/logger/component.go`); новую область
заводить там же и вписывать сюда.

| component | что покрывает |
|---|---|
| `startup` | подъём и остановка приложения |
| `http` | входящие запросы |
| `db` | обращения к базе (мост GORM → zap) |
| `auth` | разбор токена, роли, сервис-аккаунт Keycloak |
| `dislocation` | конвейер: забор ЛК/АСУ, гарды, пересборка снимка |
| `pamyatka` | памятки ГУ-45 на подачу/уборку |
| `vagonops` | история продвижения вагона (запрос 601) |
| `plan` | план подвода |
| `notify` | уведомления (колокольчик) |
| `broadcast` | отправка форм и отчётов в MAX |
| `journal` | журнал событий `event_journal` |
| `worker` | кроны и фоновые воркеры |
| `tiles` | кэш тайлов карты |

⚠️ **`component` — это ЧТО МЫ ДЕЛАЕМ, а не КУДА ХОДИМ.** Дислокация приходит
двумя путями (кабинет ЛК и шлюз АСУ) — компонент у них ОДИН, `dislocation`, а
источник виден в колонке цели. Иначе одна операция размазывается по двум
«компонентам» и не собирается грепом.

## Три слоя, которые не путать

| Слой | Где живёт | Для кого | Хранение |
|---|---|---|---|
| **Лог** | файл `log.file` + journald | инженер, разбор поломки | ротация: 100 МБ × 5 файлов × 30 дней |
| **Журнал событий** | таблица `event_journal` | диспетчер, «что происходило с дислокацией» | в базе, бессрочно |
| **Уведомления** | `notifications`, колокольчик в шапке | оператор, здесь и сейчас | 72 часа |

Правило деления: **в журнал — то, что объясняет данные** (обновление
дислокации, отказ гарда, перезагрузка справочников); **в лог — то, что
объясняет программу** (кто позвал ручку, почему она ответила 500, сколько шёл
запрос к базе). Одно и то же событие может попасть в оба места — это нормально:
журнал живёт в базе, и когда подозреваемая как раз база, смотреть больше некуда.

## Уровни

| Уровень | Что пишем | Примеры |
|---|---|---|
| `Error` | сломались мы; требуется вмешательство | 5xx у ручки, паника, отказ SQL-запроса, оборванная пересборка снимка |
| `Warn` | работа продолжается, но результат неполный или отказ осознанный | 4xx (гард, права, кривой файл), коды вне справочников, медленный запрос, порт не резолвится |
| `Info` | вехи нормальной работы, по которым восстанавливается день | старт, запрос к АСУ, «снимок пересобран», успешные ручки |
| `Debug` | трасса для разбора конкретной поломки | каждый SQL, тайлы карты, пробы healthcheck, отсутствие Bearer |

⚠️ **`level: debug` на бою не ставить.** Раньше он был безобиден (в коде было
два Debug-вызова), теперь на нём пишется трасса **каждого** обращения к базе
плюс каждый тайл и каждая проба healthcheck. Боевой конфиг (`config.vps.yaml`)
— `info`; debug включают точечно и ненадолго. На машине разработчика
(`config.local.yaml`) debug уместен — там трасса SQL и есть цель.

## Что пишется само

**Каждый HTTP-запрос** — строка `http` (`pkg/middleware/common.go`):
метод, путь, статус, длительность, `request_id`. У неуспешных добавляются
**причина** (тело ответа, до 2 КБ), `query` и `user` из токена. Причина берётся
перехватом тела, а не из хендлеров: их 39 файлов и 175 мест отвечают
`c.JSON(status, gin.H{"error": ...})` и сами ничего не логируют — перехват в
одном месте покрывает и будущие ручки, не требуя помнить про лог в каждой.

**`request_id`** приходит из заголовка `X-Request-Id` (если его поставил
ingress) либо генерируется, возвращается в ответе тем же заголовком и попадает
во **все** записи запроса — включая SQL и пересборку снимка. Разбор жалобы
диспетчера начинается с него:

```bash
grep 'req=<первые 8 знаков>' logs/service.log     # format: text
grep '"req":"<первые 8 знаков>"' logs/service.log # format: json
```

**Пересборка снимка** — итоговая строка `снимок пересобран` с длительностью и
счётчиками (`carry_new_trip`, `history_inserted`, `bros_new`, `marka_missed`…),
плюс Warn на дыры справочников. Логгер берётся из контекста: ручной запуск
(«Обновить из АСУ») сшивается с `request_id` человека, крон идёт с корневым.

**Каждый исходящий вызов** — строка с направлением `→`, именем и адресом цели
(`pkg/logger/calllog.go`, подключён в адаптерах АСУ, памяток, ЛК РЖД, Keycloak и
MAX). Раньше адаптеры молчали: пока провайдер жив, следов обращений к нему не
было вовсе, а когда падал — в файле оказывался чужой текст вроде
`dial tcp: connect: connection refused`, по которому не понять, в какой контур
мы вообще ходили. Причина отказа пишется словами («соединение отклонено»,
«таймаут», «сертификат не принят»), полный текст — в поле `error`.

⚠️ **Повторяющиеся отказы глушатся: одна строка в час на причину и клиента.**
Кроны у нас частые (АСУ — 5 минут), и без глушилки лежащий сутки провайдер дал
бы ~290 одинаковых строк на клиента — правка сделала бы лог хуже, чем был.
Когда окно истекает, число проглоченных строк уходит полем `повторов=N`, а
первый успех сбрасывает счётчик: следующий сбой снова заметен сразу.

**Веерные вызовы — в `debug`.** Очередь 601 ходит пачками по 50 вагонов, за
токеном Keycloak сервис идёт каждые несколько минут: на `info` один проход забил
бы файл. Их ИТОГ пишется одной строкой (`очередь историй пройдена`), а отказы
остаются на `warn`.

**База** — ошибки запросов и всё, что дольше `log.slow_query` (дефолт 500 мс).
Выключить порог можно отрицательным значением; ноль означает «дефолт», чтобы
стенд без этого ключа получил порог, а не тишину.

## Чего в логе намеренно нет

- **Успешных тайлов и проб** — на Info их нет (Debug), иначе healthcheck раз в
  несколько секунд и десятки тайлов на один экран карты вытесняют из файла
  работу диспетчера. Их **отказы** остаются на Warn/Error.
- **Тел успешных ответов** — выгрузка истории это 11 МБ, копировать её в память
  ради лога незачем.
- **Секретов** — токены и пароли в лог не кладём; у исходящих интеграций
  пишется только РЕЖИМ авторизации (`keycloak` / `apikey:X-API-Key` /
  `apikey:bearer`), потому что по конфигу он не вычисляется: пустой `auth_mode`
  значит разное в зависимости от того, настроен ли сервис-аккаунт.
- **Полного текста SQL** — режется до 1 КБ: пачечный INSERT снимка это сотни
  килобайт значений.
- **Имён 136 колонок отчёта ЛК** — вместо списка пишется отпечаток состава
  (`схема=a3f1c2`). Полный список печатается ТОЛЬКО когда отпечаток изменился,
  то есть ровно в тот момент, ради которого запись и заводилась: разбор идёт по
  именам полей, и молча уехавший контракт кабинета даёт кривой снимок, а не отказ.

## Куда смотреть

```bash
journalctl --user -u dpmodule-backend -f            # живой поток на VPS
grep ' ERROR ' logs/service.log | tail -50          # только поломки
grep 'снимок пересобран' logs/service.log           # история пересборок
grep ' dislocation ' logs/service.log               # весь конвейер: и ЛК, и АСУ
grep '→ ' logs/service.log                          # все походы наружу
grep 'запрос отклонён' logs/service.log             # неуспешные ручки
```

При `format: json` те же выборки идут по полям: `'"level":"error"'`,
`'"component":"dislocation"'`, `'"dir":"out"'`.
