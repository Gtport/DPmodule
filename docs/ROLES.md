# Ролевая модель (решение владельца 31.07.2026)

## Роли

Realm-роли Keycloak (claim `realm_access.roles`). Суффикс `_dpport` разводит
наш модуль от соседних в общем realm'е. Идентичность и назначение ролей —
целиком в Keycloak; таблиц пользователей в нашей БД нет.

| Роль | Кто это |
|---|---|
| `admin_dpport` | администратор системы |
| `operator_dpport` | оператор ГТ (правит данные) |
| `client_dispatcher_dpport` | диспетчер клиента |
| `client_dpport` | клиент (просмотр) |

⚠️ **Роли независимы.** Иерархии с весами больше нет: `admin_dpport` не
включает права `operator_dpport` автоматически — он попадает в набор правок
потому, что явно в нём перечислен. Кому нужны две области сразу, тому в
Keycloak назначают две роли.

## Как проверяется на сервере

Единственный источник правды — наборы доступа в `internal/auth/claims.go`:

```go
Writers = []Role{RoleOperator, RoleAdmin}  // порог правок
Admins  = []Role{RoleAdmin}                // админ-раздел
```

Раскладка гейтов — в `internal/server/server.go`:

- **Чтение** (`GET`) — любой залогиненный (валидный JWT), включая клиентские роли.
- **Любая мутация** (`POST/PUT/PATCH/DELETE`) — `RequireRolesForWrites(auth.Writers...)`
  на всей группе `/api/v1`: новая мутирующая ручка закрыта автоматически.
- **Админ-редактор справочников** `/admin/tables*` — `RequireAnyRole(auth.Admins...)`,
  включая чтение (служебный редактор, не рабочий экран).
- Точечные правила поверх наборов: правки прибытий и «Грузовой работы» не
  администратору — только сегодня/вчера (`HasRole(RoleAdmin)` в сервисах);
  гард ЛК «файл старше дислокации» обходит роль из настройки
  `reject_older_role_exempt`.

Проверка всегда fail closed: нет claims — отказ; пустой набор разрешённых
ролей — отказ даже администратору.

## Переходный период: прежние имена

Старые имена нормализуются при разборе токена (`auth.TokenRoles`), поэтому
боевой стенд продолжает работать до перевода realm'а:

| Что в токене | Во что превращается |
|---|---|
| `admin`, `administrator` | `admin_dpport` |
| `operator`, `dispatcher` | `operator_dpport` |
| `client_dispatcher` | `client_dispatcher_dpport` |
| `client` | `client_dpport` |

В `HasRole` нормализуется и сторона «что требуется», поэтому значение
`reject_older_role_exempt: "administrator"` в `client_settings` менять не
обязательно — оно по-прежнему матчит администратора. Роли пользователя там
уже канонические: их привёл `TokenRoles`.

Порядок раскатки свободный: новый бинарь понимает старые токены. Но жить на
алиасах долго не стоит — после перевода Keycloak прежние имена лучше убрать
из `legacyRoles`.

### ⚠️ Общий realm: `keycloak.strict_roles: true`

Нормализация безопасна только в СВОЁМ realm'е (боевой VPS, локальный
Keycloak), где все роли — наши. В общем realm'е стенда (`iqport`, см.
`docs/KEYCLOAK.md` §3.4) голые `admin`/`operator`/`dispatcher` — легаси-роли
всего контура: они могут быть выданы пользователям других приложений, и
нормализация подарила бы такому пользователю права `operator_dpport` или
админку. Поэтому в стендовом `config.yaml` стоит
`keycloak.strict_roles: true` — роли из токена берутся дословно, доступ дают
только точные имена `*_dpport`. Дефолт (`false`) сохраняет переходный режим
своего realm'а — конфиги боя и разработчика не меняются.

## Миграция Keycloak

1. Realm roles → Create role: `admin_dpport` («Администратор системы»),
   `operator_dpport` («Оператор ГТ»), `client_dispatcher_dpport`
   («Диспетчер клиента»), `client_dpport` («Клиент (просмотр)»).
2. Users → каждому пользователю назначить новую роль в дополнение к прежней
   (Role mapping → Assign role).
3. Убедиться, что вход и правки работают, затем удалить старые роли
   (`admin`, `operator`, `administrator`, `dispatcher`, `manager`).
4. Порядок с деплоем не важен (см. «Переходный период»), но роли лучше
   перевести в тот же день, чтобы не жить на алиасах.

На VPS Keycloak стоит без docker-обвязки нашего репо, поэтому проще через
админку; локально то же самое делалось через `kcadm.sh` в контейнере.

## Фронтенд

`core/auth/roles.ts` — константы наборов (`OPER`, `ADMIN`) и нормализация имён;
`AuthService.canEdit()` скрывает кнопки действий по тому же порогу правок.
Роль на фронте — только UI (спрятать кнопку/раздел), источник истины — гейты
бэкенда: чужая легаси-роль может показать кнопку, но правка упрётся в 403.
