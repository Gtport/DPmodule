# Ролевая модель (перенос gtport, решение владельца 28.07.2026)

## Роли и иерархия

Иерархия с весами — «старшая роль включает права младших» (как в gtport
`roleHierarchy`). Идентичность и назначение ролей — целиком в Keycloak
(realm `iqport`, realm-роли); таблиц пользователей в нашей БД нет.

| Роль | Вес | Кто это |
|---|---|---|
| `admin` | 100 | администратор системы |
| `operator` | 80 | оператор ГТ (правит данные) |
| `client_dispatcher` | 70 | диспетчер клиента (пока = client, задел на будущее) |
| `client` | 60 | клиент (просмотр) |

Роль `manager` упразднена (решение владельца). Супер-админа по логину (как в
gtport `RequireSpecificUsers("admin")`) не делаем: управление пользователями —
в админке Keycloak, приложению он не нужен.

## Как проверяется на сервере

Единственный источник правды — `internal/auth/claims.go` (веса, нормализация)
и раскладка в `internal/server/server.go`:

- **Чтение** (`GET`) — любой залогиненный (валидный JWT).
- **Любая мутация** (`POST/PUT/PATCH/DELETE`) — от `operator` и выше: гейт
  `RequireMinRoleForWrites(RoleOperator)` висит на всей группе `/api/v1`,
  новая мутирующая ручка закрыта автоматически.
- **Админ-редактор справочников** `/admin/tables*` — только `admin`
  (`RequireMinRole(RoleAdmin)`), включая чтение.
- Точечные правила поверх иерархии (без изменений): правки прибытий и
  «Грузовой работы» не-админу — только сегодня/вчера; гард ЛК «файл старше
  дислокации» обходит роль из настройки `reject_older_role_exempt`.

## Переходный период: legacy-имена

Старые realm-роли нормализуются на входе (`auth.NormalizeRole` на бэке,
`core/auth/roles.ts` на фронте): `administrator` ≡ `admin`,
`dispatcher` ≡ `operator`. Поэтому порядок раскатки свободный: новый бинарь
понимает старые токены, старый бинарь на новые роли не смотрит (для него
важен только `administrator`, который к моменту удаления уже не нужен).
Значение `reject_older_role_exempt: "administrator"` в `client_settings`
тоже продолжает работать через нормализацию — менять данные не обязательно.

## Фронтенд

- `core/auth/roles.ts` — константы `OPER = [operator, admin]`,
  `ADMIN = [admin]`, нормализация legacy-имён.
- `AuthService.canEdit()` — «порог правок»: по нему скрываются кнопки
  действий на главной (приём ЛК/АСУ, правки прибытий, грузовая работа,
  журнал брошенных, «В MAX», «Скрыть» у бесплановых, запрос 601).
- Guard'ы маршрутов: рабочие разделы (`rearrangement`, `plan`, `reference`,
  `forecasts`, …) — `OPER`; «Админ» — `ADMIN`; «Главная» — все залогиненные
  (клиент видит её в режиме просмотра).

## Миграция боевого Keycloak (сделать при раскатке ветки)

Локальный Keycloak уже переведён (и `deployments/keycloak/import/iqport-realm.json`
обновлён). На VPS — в админке Keycloak (`/admin`, realm `iqport`) руками:

1. Realm roles → Create role: `admin` («Администратор системы»),
   `client_dispatcher` («Диспетчер клиента»), `client` («Клиент (просмотр)»).
   Роль `operator` уже есть — поправить описание на «Оператор ГТ (правит данные)».
2. Users → каждому пользователю с `administrator` добавить `admin`,
   с `dispatcher` — добавить `operator` (Role mapping → Assign role).
3. Убедиться, что вход работает, затем удалить роли `administrator`,
   `dispatcher`, `manager` (Realm roles → Delete).
4. Порядок с деплоем не важен (см. «Переходный период»), но роли лучше
   перевести в тот же день, чтобы не жить на алиасах.

Тот же скрипт, что применялся локально (через `kcadm.sh` в контейнере), —
в истории ветки `feature/role-model`; на VPS Keycloak стоит без docker-обвязки
нашего репо, поэтому проще через админку.
