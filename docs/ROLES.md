# Ролевая модель (решения владельца 31.07 и 06.08.2026)

## Две схемы ролей

Идентичность и назначение ролей — целиком в Keycloak; таблиц пользователей в
нашей БД нет. Схем в токене две, и они живут раздельно:

- **Client-роли** клиента `iqport-dpport` (claim
  `resource_access["iqport-dpport"].roles`) — **основная схема** с 08.2026,
  переход по инструкции платформы (module-client-roles-howto). Роли других
  модулей на этой полке не видны в принципе, поэтому имена короткие и общие
  для всей платформы.
- **Realm-роли** с суффиксом `_dpport` (claim `realm_access.roles`) — старая
  схема. Живёт, пока платформа не выключила **Full scope allowed**; после
  этого в токене останутся только client-роли.

| Client-роль | Было (realm) | Кто это |
|---|---|---|
| `admin` | `admin_dpport` | администратор: единственный с полной админкой |
| `senior-operator` | — (не было) | оператор + правки за пределами смены + словари |
| `operator` | `operator_dpport` | оператор ГТ (правит данные в пределах смены) |
| `client-dispatcher` | `client_dispatcher_dpport` | диспетчер клиента (свои маршруты — след. итерация) |
| `client` | `client_dpport` | клиент (просмотр) |

⚠️ **Роли независимы.** Иерархии с весами нет: `admin` не включает права
`operator` автоматически — он попадает в набор правок потому, что явно в нём
перечислен. Кому нужны две области сразу, тому назначают две роли.

⚠️ **Главная ловушка: одно слово в двух схемах значит разное.** Client-роль
`operator` — наш оператор; realm-роль `operator` — платформенное легаси, висит
на чужих пользователях (`demo`). Поэтому списки ролей **нельзя складывать в
один плоский массив**: каждый список сверяется только со «своей» полкой токена.
Сторожат тесты `TestAllowsSchemasNotMixed` (бэкенд) и раундтрип
«чужая полка resource_access» (`jwt_roundtrip_test.go`).

## Матрица доступа

| Право | client | client-dispatcher | operator | senior-operator | admin |
|---|---|---|---|---|---|
| Просмотр экранов | ✔ | ✔ | ✔ | ✔ | ✔ |
| Правки данных (смена = сегодня/вчера) | — | — | ✔ | ✔ | ✔ |
| Правки за пределами смены | — | — | — | ✔ | ✔ |
| Словари marka / stations / станции перестановок / sf | — | — | — | ✔ | ✔ |
| Админка (полный реестр, все справочники) | — | — | — | — | ✔ |

Осознанное исключение: **«Подтвердить прибытие» пропавших вагонов остаётся
operator+** (решение владельца 06.08.2026) — смысл функции именно в
восстановлении старых дат дежурным диспетчером, окно смены там не действует.

## Как проверяется на сервере

Единственный источник правды — наборы доступа в `internal/auth/claims.go`
(тип `Access` — ПАРА списков client/realm, проверка `Claims.Allows`):

```go
AccessWrite      // порог правок: operator, senior-operator, admin
AccessCrossShift // за пределами смены: senior-operator, admin
AccessDicts      // словари senior'а + вход в админ-раздел: senior-operator, admin
AccessAdmin      // полный реестр админки: admin
```

Раскладка гейтов — в `internal/server/server.go`:

- **Чтение** (`GET`) — любой залогиненный (валидный JWT), включая клиентские роли.
- **Любая мутация** (`POST/PUT/PATCH/DELETE`) — `RequireForWrites(auth.AccessWrite)`
  на всей группе `/api/v1`: новая мутирующая ручка закрыта автоматически.
- **Админ-редактор** `/admin/tables*` — `Require(auth.AccessDicts)`, включая
  чтение. Внутри сервис (`service.seniorEditableTables`) отдаёт senior'у только
  его 4 словаря: `marka`, `stations`, `naznach_station` (станции перестановок),
  `sf`; чужая таблица — 403. Новая таблица реестра по умолчанию admin-only.
- Точечные правила поверх наборов (в сервисах):
  - правки прибытий и «Грузовой работы» за пределами сегодня/вчера —
    `AccessCrossShift`;
  - `PATCH /dislocation/rearrangement/stations` (drag&drop панель станций на
    «Перестановках» пишет в справочник `naznach_station`) — `AccessDicts`;
  - гард ЛК «файл старше дислокации» обходит роль из настройки
    `reject_older_role_exempt` — одно имя из данных разворачивает
    `auth.AccessFor` (матчит обе схемы).

Проверка всегда fail closed: нет claims — отказ; пустой набор разрешённых
ролей — отказ даже администратору. (Исключение: auth целиком выключен в
конфиге — claims в контексте нет, точечные правила пропускают, это dev-режим.)

`keycloak.client_id` в конфиге — чей `resource_access` читать; пусто →
берётся `keycloak.audience` (у нас совпадают, конфиги стендов не менялись).

## Переходные периоды (их два)

**1. Прежние realm-имена без суффикса** (боевой VPS, локальный Keycloak):
нормализуются при разборе токена (`auth.TokenRoles`) — `admin`/`administrator`
→ `admin_dpport`, `operator`/`dispatcher` → `operator_dpport` и т.д. В
`HasRole` нормализуется и сторона «что требуется», поэтому значение
`reject_older_role_exempt: "administrator"` менять не обязательно.

⚠️ В **общем realm'е** стенда нормализация — дыра (голые `admin`/`operator`
могут быть чужими), поэтому там `keycloak.strict_roles: true`: realm-роли
берутся дословно, доступ дают только точные `*_dpport`. **К client-ролям
strict_roles не относится** — своя полка чужой не бывает.

**2. Realm-схема → client-роли**: обе схемы читаются одновременно, порядок
раскатки свободный, откат — предыдущая версия кода. Жёсткая зависимость одна:
**до выключения Full scope allowed** платформой должны быть розданы client-роли
всем группам (см. хвост howto: `/profiles/dpport-admin` ждёт роль `admin`,
`/profiles/client` — роль `client`), иначе люди молча потеряют доступ.
Перед выключением прогнать сверку `audit-module-access.py dpport`
(скрипт платформы): изменения только в плюс, `demo` — без прав правки.

## Keycloak: что заведено

Client-роли dpport в корпоративном realm'е: `client`, `client-dispatcher`,
`operator`, `senior-operator`; `admin` — заводится (решение владельца
06.08.2026). Раздавать — на группы `/profiles/*`, не на пользователей.
Full scope НЕ выключать — это общий шаг платформы, последним.

Наш VPS и локальный Keycloak остаются на realm-схеме (старые имена +
нормализация) — там ничего заводить не нужно, код понимает обе схемы.

## Фронтенд

`core/auth/roles.ts` — наборы `RoleSet` (пары client/realm: `OPER`, `DICTS`,
`ADMIN`, `ANY`) и нормализация realm-имён; проверка — `AuthService.allows(set)`
(зеркало `Claims.Allows`), порог кнопок — `canEdit()`. Меню и маршрут «Админ» —
`DICTS`: senior входит, список таблиц отдаёт сервер уже отфильтрованным.
Каталог модулей (`modules.config.ts`) несёт `roles` (realm) и `clientRoles`
раздельно; module-switcher проверяет чужой модуль по полке его клиента
`iqport-<id>`. Роль на фронте — только UI (спрятать кнопку/раздел), источник
истины — гейты бэкенда: чужая роль может показать кнопку, но правка упрётся в 403.
