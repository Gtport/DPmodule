# Мультитенантная архитектура платформы: адресация, Keycloak, БД

> Как разворачивать модули (dpport, rtport, mpport, rwgate, …) для многих
> заказчиков с разным числом терминалов на одном доменном имени.
> Сначала — краткая версия для принятия решения, дальше — подробный разбор
> с примерами конфигов.

---

## Краткая версия

**Единица развёртывания — «инстанс» = модуль + зона обслуживания.**
Не «модуль» (dpport один на три терминала, rtport — на каждый свой) и не
«терминал» (mpport обслуживает полтора терминала). У инстанса одно имя,
и оно используется везде: в URL, в имени контейнеров, в схеме БД, в клиенте
Keycloak.

**Формула:**

| Уровень | Что получает |
|---|---|
| Заказчик | поддомен + realm в Keycloak + база данных |
| Инстанс модуля | URL-префикс + клиент Keycloak + схема в БД + пара контейнеров (бэк+фронт) |
| Терминал внутри общего инстанса | группа в Keycloak → claim в токене |

**Пример для заказчика edc (терминалы АЭ, ГУТ-2, УТ-1):**

| Инстанс | URL | Схема БД | Клиент Keycloak |
|---|---|---|---|
| `dpport` (все 3 терминала) | `edc.domain.ru/dpport/` | `dpport` | `dpport` |
| `rtport-ae` | `edc.domain.ru/rtport-ae/` | `rtport_ae` | `rtport-ae` |
| `rtport-gut2` | `edc.domain.ru/rtport-gut2/` | `rtport_gut2` | `rtport-gut2` |
| `rtport-ut1` | `edc.domain.ru/rtport-ut1/` | `rtport_ut1` | `rtport-ut1` |
| `mpport-ut1` | `edc.domain.ru/mpport-ut1/` | `mpport_ut1` | `mpport-ut1` |
| `mpport-ae-gut2` | `edc.domain.ru/mpport-ae-gut2/` | `mpport_ae_gut2` | `mpport-ae-gut2` |
| `rwgate` (провайдер) | `edc.domain.ru/rwgate/` | `rwgate` | `rwgate` (service account) |

**Keycloak один на всех**, живёт на `auth.domain.ru`. Realm на заказчика
(изоляция пользователей), клиент на инстанс (роли клиента = права в модуле),
вход по Authorization Code + PKCE, SSO внутри realm: пользователь логинится
один раз и попадает во все модули, где у него есть роли.

**«Одно доменное имя»** — это один купленный домен `domain.ru`; поддомены
заказчиков (`edc.domain.ru`, `auth.domain.ru`) закрываются одним
wildcard-сертификатом `*.domain.ru`.

**Что нужно доработать в модулях**, чтобы один docker-образ подходил любому
инстансу без пересборки:

1. фронт читает адрес Keycloak, realm, clientId и префикс API из
   `assets/config.json`, который контейнер генерирует при старте из переменных
   окружения (сейчас адрес зашивается в бандл при сборке — это блокер);
2. `<base href>` подставляется в `index.html` тоже при старте контейнера;
3. бэк получает имя инстанса через конфиг/окружение (оно же префикс URL,
   схема БД, clientId).

Масштабирование = добавление строк в таблицу инстансов, а не переделка
архитектуры. «dpport на каждый терминал» завтра — это просто три инстанса
`dpport-ae`, `dpport-gut2`, `dpport-ut1`.

## Обоснование: сравнение с вариантом rtport

В rtport реализован другой подход — **мультитенантность внутри приложения**.
Один бэкенд-процесс обслуживает все терминалы: в конфиге карта `tenants:`
(gut2, ut1) с отдельной *базой* на терминал, и на каждый запрос бэк выбирает
базу по группе Keycloak вошедшего пользователя (`groups: /gut-2` → tenant
`gut2`). Keycloak — один realm `iqport` на всю платформу, клиент на модуль
(`iqport-rtport` с проверкой audience), роли — **realm-роли** (operator /
dispatcher / manager / administrator). Фронт — курс на монорепо apps+libs
с отдельной сборкой на клиента (`ng build gut`), адрес Keycloak зашивается
в бандл при сборке.

### Чем вариант rtport хорош

- **Дёшев в эксплуатации:** один процесс вместо трёх; новый терминал —
  несколько строк в конфиге, без новых контейнеров.
- Фоновые задачи по всем терминалам сразу (сводные отчёты, кроны) — процесс
  и так видит все базы.
- Проверка `audience` в токене — грамотная практика, берём себе (§3.4).
- Монорепо apps+libs — правильный ответ на *другой* вопрос: что делать,
  когда у клиентов расходится доменная логика. Это про организацию кода,
  и с настоящей схемой оно совместимо.

### Почему как архитектура платформы он не годится

Вариант rtport решает узкую задачу «один модуль на одном стенде обслуживает
два терминала». Вопрос платформы — «много заказчиков × комбинации модулей ×
один домен» — он не закрывает:

1. **Оси «заказчик» нет вообще.** Realm один, tenants — это терминалы
   одного заказчика. Второй заказчик означает либо чужих пользователей
   в том же realm (люди разных компаний в одном списке; делегировать
   заказчику админку своих пользователей безопасно нельзя), либо второй
   стенд целиком — с пересборкой бандлов, потому что адрес Keycloak зашит
   в `environment.production.ts`.
2. **Realm-роли — дыра между модулями.** Роль `dispatcher` в realm одна
   на всех: выдали её для rtport — она действует в любом модуле, который
   проверяет realm-роли (эта дыра уже находилась на стендовом Keycloak).
   Требование «у пользователя свои права в каждом модуле» выполняют только
   **client-роли** (§3.2): роли клиента `rtport-ut1` не видны клиенту
   `dpport` в принципе.
3. **Выбор базы по токену на каждый запрос — риск утечки между
   терминалами.** Каждый обработчик обязан не забыть взять правильную БД из
   реестра по группе пользователя; одна ошибка (пропущенная проверка, общий
   кэш без ключа тенанта) — и диспетчер УТ-1 видит данные ГУТ-2. При
   изоляции на уровне развёртывания у процесса физически один DSN —
   перепутать нечего. Плюс радиус поражения: неудачная выкатка одного
   бинаря кладёт все терминалы сразу; версионировать и масштабировать их
   независимо нельзя.
4. **Адресация «N заказчиков на одном домене» не решена.** Есть один стенд
   с зашитым в сборку адресом; схемы поддомен/префикс/runtime-конфиг там
   нет — а это и есть предмет настоящего документа.
5. **Сборка на клиента множит артефакты.** `ARG APP=gut` → образ на каждого
   клиента × каждый стенд. При двух клиентах терпимо, при росте —
   комбинаторика. Наш инвариант — «один образ — любой инстанс» (§2.3);
   если клиенты действительно разошлись кодом, их сборки становятся просто
   разными *модулями* в таблице инстансов.

### Подходы не исключают друг друга

Схема инстансов не запрещает мультитенантный rtport: тогда он — одна строка
`rtport` в таблице (как dpport: один на все терминалы, терминал — через
claim, §3.3) вместо трёх строк `rtport-ae/-gut2/-ut1`. Решение «инстанс на
терминал или один на всех» остаётся за каждым модулем и может меняться со
временем — платформа от этого не зависит. А realm-на-заказчика, client-роли,
адресация и runtime-конфиг — то, чего в варианте rtport нет и что при
появлении второго заказчика придётся делать в любом случае.

## Подробный разбор

Дальше — то же самое, но с объяснением *почему* и с примерами конфигов.
Рассчитано на разработчика, который будет это внедрять.

### 1. Почему единица — «инстанс», а не модуль или терминал

Если строить адресацию вокруг **модуля** (`/dpport/`, `/rtport/`), ломаемся
на rtport: их три штуки, и по одному пути их не различить. Если вокруг
**терминала** (`/ut1/dpport/`), ломаемся на dpport и rwgate: они одни на все
терминалы, и непонятно, по какому из трёх путей их вешать. mpport ломает оба
варианта сразу — он «один на АЭ+ГУТ-2 и один на УТ-1».

Поэтому вводим понятие **инстанс**: конкретное развёртывание модуля с
конкретной зоной обслуживания. Имя инстанса строится по конвенции:

```
{модуль}[-{зона}]
  dpport            зона не указана = «все терминалы заказчика»
  rtport-ut1        один терминал
  mpport-ae-gut2    группа терминалов
```

Это имя — **несущая конвенция** всей схемы. Из него механически выводятся:

- URL-префикс: `/{имя-инстанса}/`
- имена контейнеров: `{заказчик}-{имя-инстанса}-back`, `…-front`
- схема в БД: имя инстанса, где дефисы заменены на `_` (в Postgres дефис
  в идентификаторе требует кавычек, лучше не связываться)
- clientId в Keycloak: имя инстанса как есть

Правило одно: **придумал имя инстанса — больше нигде ничего не придумываешь.**
Любое место, где имя «почти такое же, но чуть другое», через полгода
превращается в загадку.

### 2. Адресация и маршрутизация

#### 2.1. Схема URL

```
https://edc.domain.ru/dpport/           SPA-фронт dpport
https://edc.domain.ru/dpport/api/...    REST API бэка dpport
https://edc.domain.ru/rtport-ut1/       SPA-фронт rtport для УТ-1
https://edc.domain.ru/rtport-ut1/api/…  его бэк
https://auth.domain.ru/realms/edc/...   Keycloak, realm заказчика edc
```

Заказчик — **поддомен**, инстанс — **путь**. Почему именно так:

- **Изоляция cookies.** Cookies ставятся на хост. Если все заказчики живут
  на путях одного хоста (`domain.ru/edc/…`, `domain.ru/xxx/…`), браузер
  пользователя, работающего с двумя заказчиками, будет слать cookies обоих
  в оба — источник трудноуловимых багов с сессиями и CSRF.
- **Redirect URI и CORS проще и жёстче.** У клиента Keycloak redirect URI
  вида `https://edc.domain.ru/dpport/*` — и токен физически невозможно
  получить с хоста другого заказчика.
- **Свой домен заказчика** (`port.zakazchik.ru` → CNAME на наш) вешается без
  переделок: добавили hostname в прокси и в redirect URI клиента, всё.
- Один wildcard-сертификат `*.domain.ru` (Let's Encrypt DNS-01) закрывает
  всех заказчиков — по сертификату на заказчика выпускать не нужно.

Если поддомены по каким-то причинам запрещены, схема деградирует до
`domain.ru/{заказчик}/{инстанс}/` — работает, но изоляцию cookies и CORS
придётся компенсировать аккуратностью (path-scoped cookies, строгие списки
origin'ов). Это запасной вариант, не основной.

#### 2.2. Реверс-прокси

На входе стоит один реверс-прокси, который по хосту и префиксу пути
раскидывает запросы по контейнерам. Два варианта:

**nginx** (как сейчас на VPS) — работает, но на каждый новый инстанс нужно
руками дописывать `location` в центральный конфиг:

```nginx
# фрагмент для одного инстанса; таких блоков — по числу инстансов
server {
    server_name edc.domain.ru;

    location /rtport-ut1/api/ {
        proxy_pass http://edc-rtport-ut1-back:8080/api/;
    }
    location /rtport-ut1/ {
        proxy_pass http://edc-rtport-ut1-front:80/;
    }
    # ... dpport, mpport-ut1, ...
}
```

**Traefik** (рекомендация при росте числа инстансов) — маршрут описывается
метками прямо в compose-файле самого инстанса, центральный конфиг никто
не трогает:

```yaml
# deployments/edc/docker-compose.yml (фрагмент)
services:
  rtport-ut1-front:
    image: registry.local/rtport-front:1.4.0
    environment:
      BASE_HREF: /rtport-ut1/
      KC_URL: https://auth.domain.ru
      KC_REALM: edc
      KC_CLIENT_ID: rtport-ut1
      API_BASE: /rtport-ut1/api
    labels:
      - traefik.enable=true
      - traefik.http.routers.edc-rtport-ut1-front.rule=Host(`edc.domain.ru`) && PathPrefix(`/rtport-ut1/`)

  rtport-ut1-back:
    image: registry.local/rtport-back:1.4.0
    environment:
      INSTANCE: rtport-ut1
      PG_DSN: postgres://rtport_ut1@db:5432/edc?search_path=rtport_ut1
      KC_ISSUER: https://auth.domain.ru/realms/edc
      KC_CLIENT_ID: rtport-ut1
    labels:
      - traefik.enable=true
      - traefik.http.routers.edc-rtport-ut1-back.rule=Host(`edc.domain.ru`) && PathPrefix(`/rtport-ut1/api/`)
```

Приоритет маршрутов у Traefik по длине правила, поэтому `/rtport-ut1/api/`
сам выигрывает у `/rtport-ut1/` — порядок блоков не важен.

**Один compose-файл (или stack) = один заказчик.** Вся инсталляция edc —
это `deployments/edc/docker-compose.yml` со всеми его инстансами. Новый
заказчик — новый файл по шаблону.

#### 2.3. Что нужно от фронтенда: base href и runtime-конфиг

SPA, собранная «под корень», не заработает под `/rtport-ut1/`: побьются пути
к статике и роутинг. И это **нельзя** решать сборкой отдельного бандла на
каждый инстанс — тогда число сборок = число инстансов × число заказчиков.

Цель: **один docker-образ фронта — любой инстанс.** Для этого при старте
контейнера entrypoint-скрипт подставляет значения из переменных окружения:

```sh
#!/bin/sh
# entrypoint фронт-контейнера (nginx с раздачей статики)
set -e
# 1) base href в index.html
sed -i "s|<base href=\"/\">|<base href=\"${BASE_HREF}\">|" /usr/share/nginx/html/index.html
# 2) runtime-конфиг для приложения
cat > /usr/share/nginx/html/assets/config.json <<EOF
{
  "keycloak": {
    "url": "${KC_URL}",
    "realm": "${KC_REALM}",
    "clientId": "${KC_CLIENT_ID}"
  },
  "apiBase": "${API_BASE}"
}
EOF
exec nginx -g 'daemon off;'
```

А приложение при старте (в Angular — через `APP_INITIALIZER` /
`provideAppInitializer`) загружает `assets/config.json` и инициализирует
OAuth-клиент и HTTP-слой из него — вместо импорта `environment.production.ts`.

> Сейчас в dpport адрес Keycloak зашит в `environment.*.ts` на этапе сборки —
> из-за этого на каждый стенд нужна своя сборка бандла. Переход на
> runtime-конфиг убирает эту проблему целиком и является **предусловием**
> всей схемы.

#### 2.4. Что нужно от бэкенда

Бэк и так конфигурируется окружением (systemd/compose). Добавляется понятие
«имя инстанса», из которого он знает:

- свой URL-префикс (`/rtport-ut1` — чтобы корректно строить ссылки и,
  при необходимости, страйпить префикс);
- свою схему БД (`search_path=rtport_ut1` прямо в DSN);
- свой clientId — у какого клиента проверять роли в токене (см. §3.4).

### 3. Аутентификация: Keycloak

Один сервер Keycloak на весь хостинг, на отдельном поддомене
`auth.domain.ru`. Внутри — три уровня. Здесь — *что* настраивается и
*почему*; пошаговая инструкция по кликам админ-консоли —
[`KEYCLOAK_REALM_SETUP.md`](KEYCLOAK_REALM_SETUP.md).

#### 3.1. Realm = заказчик

Realm в Keycloak — полностью изолированное пространство: свои пользователи,
свои клиенты, свои сессии, свой админ. Заводим **realm на заказчика**:
`edc`, дальше по одному на каждого нового.

Что это даёт:

- пользователи заказчиков не видят и не пересекают друг друга даже
  теоретически;
- заказчику можно выдать делегированного администратора **его** realm
  (роль `realm-management/manage-users`) — он сам заводит своих людей и
  раздаёт группы, не имея доступа к чужим realm и к настройкам клиентов;
- новый заказчик = импорт realm-шаблона (JSON-экспорт с клиентами, ролями
  и группами, без пользователей) + правка имён. Механика импорта у нас уже
  отработана в `deployments/keycloak/import/`.

Realm `master` — только для нас (платформенных админов), в нём не живёт
ни один пользователь заказчика.

#### 3.2. Клиент = инстанс модуля

В realm заказчика заводится **клиент на каждый инстанс**: `dpport`,
`rtport-ae`, `rtport-gut2`, `rtport-ut1`, `mpport-ut1`, `mpport-ae-gut2`.

- Тип — public client, вход по **Authorization Code + PKCE** (наш
  платформенный стандарт; ROPC и собственные формы логина упразднены).
- Valid redirect URIs: `https://edc.domain.ru/rtport-ut1/*`;
  Web origins: `https://edc.domain.ru`. Жёстко, без `*` на весь мир.
- **Роли клиента** (client roles) — это права пользователя в этом модуле:
  `dispatcher`, `administrator`, `viewer`, … У каждого клиента свой набор,
  наборы разных модулей независимы.

Почему клиент на инстанс, а не один клиент на заказчика: права нужны
**в каждом модуле свои** (условие задачи). Роли клиента `rtport-ut1` никак
не пересекаются с ролями `dpport`, бэк каждого инстанса смотрит только
в свой блок `resource_access` токена — путаница исключена конструктивно.

При этом внутри одного realm работает **SSO**: пользователь логинится один
раз (на `auth.domain.ru`), и при переходе в любой другой модуль, где у него
есть роли, повторный ввод пароля не нужен — Keycloak молча выдаёт токен для
следующего клиента.

`rwgate` — особый случай: это провайдер, а не пользовательское приложение.
Ему заводится **confidential client с service account** (grant type
`client_credentials`): бэки модулей ходят в него по машинному токену, формы
логина у него нет.

#### 3.3. Терминал внутри общего инстанса = группа → claim

dpport один обслуживает три терминала, значит «к какому терминалу пользователь
имеет доступ» — это не отдельный инстанс, а **атрибут пользователя внутри
инстанса**. Решается группами:

```
Группы realm edc:
  /terminals/ae
  /terminals/gut2
  /terminals/ut1
```

На клиенте `dpport` настраивается protocol mapper, который кладёт членство
в этих группах в claim токена:

```json
{ "terminals": ["ut1", "gut2"] }
```

Бэк dpport фильтрует данные по этому claim'у. Для админа заказчика управление
выглядит по-человечески: «добавил пользователя в группу УТ-1 — он видит УТ-1»,
никаких ролей руками.

Для модулей, у которых инстанс и так на один терминал (rtport-ut1), claim
не нужен: сам факт наличия роли в клиенте уже означает доступ к терминалу.

#### 3.4. Проверка токена на бэке

Каждый бэк-инстанс проверяет:

1. подпись и срок токена по issuer своего realm:
   `https://auth.domain.ru/realms/edc` (JWKS кэшируется);
2. роли — только из `resource_access["<свой clientId>"].roles`;
3. для мульти-терминальных модулей — claim `terminals`.

Никакой пользовательской БД на бэке нет: Keycloak — единственный источник
истины про пользователей и права.

### 4. База данных

Как и принято в платформе: **база на заказчика, схема на инстанс.**

```
База edc:
  схема dpport
  схема rtport_ae
  схема rtport_gut2
  схема rtport_ut1
  схема mpport_ut1
  схема mpport_ae_gut2
  схема rwgate
```

Дополнительно — **роль БД на инстанс** с правами только на свою схему
(`GRANT ALL ON SCHEMA rtport_ut1 TO rtport_ut1_app`, и ничего сверх).
Тогда баг или инъекция в одном модуле физически не дотянется до данных
другого. В DSN бэка схема задаётся через `search_path` (см. пример compose
в §2.2) — код модуля про имя схемы не знает, миграции катаются в текущую
схему подключения.

Один сервер Postgres на всех заказчиков — нормально до заметных нагрузок;
если какой-то заказчик вырастет, его базу можно унести на отдельный сервер,
не меняя ничего, кроме DSN.

### 5. Чек-листы

#### Новый заказчик

1. DNS: `{заказчик}.domain.ru` → наш IP (при wildcard-записи — ничего).
2. Keycloak: импорт realm-шаблона под именем заказчика, правка redirect URI
   (пошагово — [`KEYCLOAK_REALM_SETUP.md`](KEYCLOAK_REALM_SETUP.md)).
3. Postgres: `CREATE DATABASE {заказчик}`, схемы и роли по списку инстансов.
4. `deployments/{заказчик}/docker-compose.yml` по шаблону: перечислить
   инстансы, заполнить окружение.
5. `docker compose up -d`. Прокси (Traefik) подхватит маршруты сам.

#### Новый инстанс у существующего заказчика

1. Придумать имя по конвенции `{модуль}[-{зона}]` — единственное творческое
   действие.
2. Keycloak: новый клиент с этим именем, роли, redirect URI
   ([`KEYCLOAK_REALM_SETUP.md`](KEYCLOAK_REALM_SETUP.md), §3).
3. БД: схема + роль.
4. Пара сервисов в compose заказчика, `up -d`.

#### Предусловия в коде модулей (разовая доработка)

- [ ] Фронт: runtime-конфиг `assets/config.json` вместо зашитых
      `environment.*.ts` (Keycloak, apiBase).
- [ ] Фронт: подстановка `<base href>` в entrypoint контейнера.
- [ ] Бэк: имя инстанса в конфиге; схема — через `search_path` в DSN;
      clientId для проверки ролей — из конфига.
- [ ] Мульти-терминальные модули: чтение claim `terminals` и фильтрация.

### 6. Типовые вопросы

**Почему не отдельный Keycloak на заказчика?** Дорого в сопровождении
(обновления, бэкапы, мониторинг × N) и не даёт ничего сверх изоляции realm.
Отдельный Keycloak оправдан только если заказчик требует хостинг своей
инфраструктуры у себя — тогда его compose просто указывает на другой
`KC_URL`, схема это переживает без изменений.

**Что если заказчик захочет вход через свой корпоративный AD/SSO?** В его
realm добавляется Identity Provider (SAML/OIDC-федерация) — это настройка
realm, остальная схема не меняется.

**Как это соотносится с текущим VPS (95850.koara.live)?** Текущий стенд —
частный случай схемы: один заказчик, один инстанс (dpport), префикс `/`,
Keycloak на том же хосте. Миграция — это переезд на wildcard-домен и
вынос Keycloak на `auth.*`; порядок переезда — отдельная задача, здесь
не описан.
